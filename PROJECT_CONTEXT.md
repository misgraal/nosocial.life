# Контекст проекта NoSocial.life

Актуализировано: 30 октября 2026 года. Основано на коде текущего checkout, а не на состоянии работающего сервера. Документ предназначен для быстрого знакомства разработчика или AI-ассистента с проектом.

## 1. Назначение и реализованные возможности

NoSocial.life — самостоятельно размещаемое домашнее облачное хранилище с веб-интерфейсом и медиасервером DLNA/UPnP. Метаданные хранятся в MySQL, содержимое файлов — на дисках сервера. Целевая серверная среда — Ubuntu Linux; конфигурация также учитывает macOS и Windows.

В текущем коде реализованы:

- Регистрация, вход, выход, роли `user` и `admin`, блокировка пользователей.
- Личные файлы и папки, дерево каталогов, хлебные крошки, поиск, сортировка и переключение вида списка.
- Создание папок, переименование, перемещение и удаление объектов; скачивание файлов и папок в ZIP.
- Загрузка файлов и директорий частями с прогрессом, скоростью, оценкой оставшегося времени, проверкой статуса и отменой.
- Публичные ссылки на файлы и папки, срок действия, пароль, настройка скачивания для файлов.
- Предоставление доступа конкретным пользователям по имени и раздел общих объектов.
- Общая публичная медиапапка `Movies` со стабильным `publicID=movies`.
- Просмотр изображений, видео, PDF, текста и таблиц `.xlsx`, `.csv`, `.tsv`; фактическое воспроизведение зависит от браузера и формата.
- Генерация JPEG-превью изображений и видео через `ffmpeg`.
- Админ-панель: пользователи, роли, блокировки, квоты, выбор дисков для загрузки, просмотр объектов пользователей, отзыв публичных ссылок, аудит и диагностика.
- Просмотр пользовательских сессий и завершение остальных сессий.
- PWA manifest, service worker, светлая и тёмная темы.
- Docker Compose, автоматическое развёртывание через GitHub Actions, DLNA; опциональный Jellyfin.

## 4. Архитектура и точки входа

Типичный путь запроса:

```text

                                          └───────────────→ файловая система / ffmpeg
```

Точка запуска — `app.main:app`. Роутеры объединяются в [app/web/__init__.py](app/web/__init__.py).

Основные модули:

| Файл | Ответственность |
| --- | --- |

| [app/services/app.py](app/services/app.py) | Dataclass-payload, дерево папок, поиск, переименование, перемещение, общие проверки |
| [app/services/files.py](app/services/files.py) | Выбор диска, chunk upload, квоты, удаление, доступ к файлам, MIME и превью |
| [app/services/folders.py](app/services/folders.py) | Корневая папка, общая Movies, содержимое и дерево папок, наследование доступа, ZIP |
| [app/services/media_storage.py](app/services/media_storage.py) | Физические каталоги Movies, перенос файлов и обновление путей при перемещении и переименовании, откат при ошибке БД |
| [app/services/admin.py](app/services/admin.py) | Проверка роли, управление пользователями и дисками, диагностика |

## 5. Данные и хранение

Актуальная схема и миграции определены в `app/db/db.py`. Отдельного инструмента вроде Alembic нет; выполненные миграции отмечаются в `schema_migrations`. Соединения используют `autocommit=True`.

| Таблица | Назначение |
| --- | --- |
| `users` | Имя, хеш пароля, роль, блокировка, квота `storageQuotaBytes` |
| `folders` | Владелец, родитель, имя, `publicID`, публичность, срок и пароль ссылки |
| `files` | Владелец, папка, имя, физический `serverPath`, размер `BIGINT`, `previewPath`, настройки ссылки |
| `upload_disks` | Пути дисков и флаг разрешения загрузок |
| `file_user_shares` | Получатели персонального доступа к файлам |
| `folder_user_shares` | Получатели персонального доступа к папкам |
| `audit_logs` | События, пользователь, объект, детали и время |
| `schema_migrations` | Применённые миграции |

`fileID`/`folderID` — внутренние числовые ключи; `publicID` используется в URL и клиентских операциях. Наличие `publicID` само по себе не предоставляет доступ.

Важные особенности физического хранения:

- Обычная иерархия папок преимущественно логическая: файлы сохраняются в корне выбранного диска, а принадлежность папке задаётся в БД.
- Для Movies загрузка формирует физический путь `<disk>/Movies/<подпапки>`, доступный медиасерверу.
- Создание папки в Movies создаёт физический каталог; перемещение и переименование синхронизируют файлы и пути БД. При удалении папки её опустевшие физические каталоги удаляются; неучтённые в БД файлы рекурсивно не стираются.
- При совпадении физического имени используется префикс upload ID.
- Временные данные: `<disk>/<temp>/chunks/<userID>_<uploadId>/`.
- JPEG-превью кешируются в `runtime/previews/`.
- Сессии сохраняются в `runtime/sessions.json`, ключ подписи публичного доступа — в `runtime/share-signing.key`.

БД и файловое хранилище нужно учитывать совместно: записи содержат физические пути. Перенос данных между окружениями требует проверки этих путей.

## 6. Ключевые сценарии

### Аутентификация и сессии

Регистрация проверяет имя длиной 3–64 символа из `A–Z`, `a–z`, цифр, `_.@-`; пароль должен быть непустым, подтверждение — совпадать. Пароли хешируются Argon2. Поиск имени при регистрации и входе регистронезависимый.

Особое правило текущего кода: пользователь с именем `admin` получает роль администратора при регистрации; при инициализации схемы эта роль также восстанавливается для такого имени.

Cookie `session_id` имеет `HttpOnly`, `SameSite=Lax`, срок 7 дней и настраиваемый `Secure`. Сессии находятся в памяти процесса и сохраняются в JSON. Rate limiting входа и регистрации также находится в памяти процесса.

### Загрузка файлов

Клиентская логика расположена главным образом в `app/templates/app.html`. Размер части — 8 MiB. Upload ID сохраняется в `localStorage`; клиент запрашивает сохранённые части перед продолжением.

Сервер проверяет параметры частей, изолирует upload ID префиксом пользователя, выбирает разрешённый диск и записывает части на диск. Поддерживаются запись по смещению в `upload.data` с маркерами `.done` и старый вариант отдельных `.part`.

После последней части проверяются наличие частей, итоговый размер и квота, определяется папка назначения, создаётся итоговый файл и запись в БД, добавляется событие аудита. Для Movies файл становится публичным автоматически.

Выбор хранилища учитывает свободное место и объём уже записанных файлов: для разных устройств приоритет у большего свободного места; для путей одного устройства — у меньшего учтённого объёма. Новые диски из конфигурации первоначально добавляются в БД выключенными.

Очистка незавершённых загрузок вызывается на старте и при загрузке, с интервалом проверки 30 минут; порог возраста каталога — 24 часа. Это не отдельный фоновый планировщик.

### Совместный и публичный доступ

Следует различать владельца, персонального получателя и посетителя публичной ссылки. Вход в систему сам по себе не даёт доступ к чужому закрытому файлу.

Публичная папка предоставляет доступ к вложенному дереву и файлам, даже когда собственный флаг `public` у потомка выключен. Пароль и срок действия публичного предка участвуют в проверке этого доступа. Персональный доступ к папкам также учитывает предков.

После ввода пароля выдаётся подписанный HMAC-SHA256 токен на 12 часов, привязанный к типу объекта, `publicID` и текущему хешу пароля. Проверяются подпись и срок токена. Изменение пароля делает старое разрешение недействительным.

Для публичного скачивания файла проверяется `publicAllowDownload`. Флаг управляет endpoint скачивания и включением в публичный ZIP; доступ к содержимому для разрешённого просмотра остаётся отдельным сценарием.

Movies — одна каноническая публичная папка для всех пользователей. При обеспечении этой папки код объединяет найденные дубликаты записей. Изменения здесь затрагивают общую медиатеку.

### Просмотр и PWA

Содержимое отдаётся через `FileResponse` с определением MIME. Для inline content задаются CSP `sandbox`, `X-Content-Type-Options: nosniff` и `Cache-Control: private, no-store`. Создание миниатюр выполняется через thread pool.

Текстовый preview ограничен 500 000 символами; табличный — 100 строками и 20 столбцами. Для XLSX читается первый лист через ZIP/XML стандартной библиотеки.

Service worker обслуживает только GET-запросы к `/static/`: сначала сеть, при ошибке — кеш. HTML-страницы, API и пользовательские файлы этим механизмом не кешируются для автономной работы.

## 8. Конфигурация окружения

Настройки читаются из окружения в [config.py](config.py) и `app/db/db.py`.

| Переменная | Значение по умолчанию / смысл |
| --- | --- |
| `DB_HOST`, `DB_PORT` | `127.0.0.1`, `3306`; Compose переопределяет host на `mysql` |
| `DB_NAME` | `nosocial` |
| `DB_USER`, `DB_PASSWORD` | Значения для подключения к БД; задать для своего окружения |
| `DB_ROOT_PASSWORD` | Пароль root при создании контейнера MySQL |
| `NOSOCIAL_STORAGE_DIRS` | Linux: `/mnt/storage`; Windows: `H:/`; macOS: `<repo>/files` |
| `NOSOCIAL_TMP_FOLDER` | `temp` |
| `NOSOCIAL_MEDIA_FOLDER` | `Movies` |
| `NOSOCIAL_MEDIA_FOLDER_PUBLIC_ID` | `movies` |
| `NOSOCIAL_COOKIE_SECURE` | `false` в Python-конфигурации; пример серверного env включает `true` |
| `NOSOCIAL_LOGIN_RATE_LIMIT_ATTEMPTS` | `8` |
| `NOSOCIAL_LOGIN_RATE_LIMIT_WINDOW_SECONDS` | `300` |

Несколько storage-путей можно разделять запятыми; также поддерживается системный разделитель `os.pathsep`. Относительные пути разрешаются от корня проекта. `RUNTIME_DIR` фиксирован как `<repo>/runtime`.

Пример серверного окружения: [docker_server/.env-example](docker_server/.env-example). Сам Python-код `.env` автоматически не загружает; Compose передаёт его через `env_file`. Фактические пароли, токены, содержимое сессий и ключ подписи в этот документ не включаются.

## 9. Локальный запуск

Нужны Python 3.12 для соответствия образу, доступный MySQL и `ffmpeg` для медиапревью. База и пользователь БД должны существовать заранее; таблицы и миграции создаст приложение.

Из корня репозитория, в POSIX shell:

```bash
python3 -m venv venv
source venv/bin/activate
python -m pip install -r requirements.txt

export DB_HOST=127.0.0.1
export DB_PORT=3306
export DB_NAME=nosocial
export DB_USER=nosocial
export DB_PASSWORD='replace-with-local-password'
export NOSOCIAL_STORAGE_DIRS="$PWD/files"
export NOSOCIAL_COOKIE_SECURE=false

python -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

Открыть `http://127.0.0.1:8000`, зарегистрировать администратора с именем `admin`, затем выбрать и сохранить хотя бы один диск в `Admin > Disk usage`. Без включённого диска загрузка отклоняется. Для локального HTTP нужен `NOSOCIAL_COOKIE_SECURE=false`.

## 10. Docker и развёртывание

[Dockerfile](Dockerfile) устанавливает зависимости, `ffmpeg` и MiniDLNA, копирует `app/` и `config.py`, запускает Uvicorn на порту 8000. В контейнере корень приложения — `/`, поэтому runtime находится в `/runtime`.

[docker_server/docker-compose.yml](docker_server/docker-compose.yml) использует опубликованный образ `ghcr.io/misgraal/nosocial.life:latest`; секции `build` в нём нет.

- `mysql`: MySQL 8.4, том `mysql_data`, порт `127.0.0.1:3306`.
- `app`: FastAPI, порт `127.0.0.1:8000`, bind mount `/mnt/storage`, том `app_runtime:/runtime`.
- `dlna`: тот же образ с запуском MiniDLNA и пересканированием существующего индекса при старте (`-r`), host network, чтение `/mnt/storage` через `/media/storage:ro`.
- `jellyfin`: опциональный profile `jellyfin`, порт 8096, медиатека `/mnt/storage/Movies` только для чтения.
- `video-optimizer`: опциональный profile `tools`, скрипт remux для fast-start MP4/MOV.

Подготовка конфигурации и запуск на Linux-сервере с доступным `/mnt/storage`:

```bash
cd docker_server
cp .env-example .env
# Указать собственные значения в .env перед запуском.
docker compose config --quiet
docker compose up -d mysql app dlna
# Опционально:
docker compose --profile jellyfin up -d jellyfin
```

При обычной HTTP-проверке следует выставить `NOSOCIAL_COOKIE_SECURE=false`; при HTTPS — `true`. Compose публикует приложение только на loopback; для внешнего доступа нужен отдельно настроенный reverse proxy/TLS. Его конфигурация в репозитории не представлена.

Workflow [deploy.yml](.github/workflows/deploy.yml) запускается при push в `main` или вручную: собирает образ, отправляет в GHCR, копирует серверные конфиги и выполняет pull/up через SSH. Нужны secrets `SERVER_HOST`, `SERVER_USER`, `SERVER_SSH_KEY`, `GHCR_PAT`; SSH-порт задан как `4555`, серверный каталог — `/home/nosocial/app`. Серверный `.env` workflow не создаёт.

MiniDLNA сканирует `/media/storage/Movies`, использует порт 8200 и host network для обнаружения в локальной сети. Адреса DLNA/Jellyfin частично заданы под конкретную домашнюю сеть в конфигурации и диагностике.

## 11. Проверки и эксплуатационные особенности

Существующие регрессионные тесты запускаются из корня с установленными зависимостями:

```bash
python -m unittest discover -s tests -v
```

Практические ограничения текущей реализации:

- Сессии, rate limiting и часть состояния загрузок используют память процесса. Перед запуском нескольких worker/реплик требуется проработать согласованность; JSON-файл сессий не является общим транзакционным хранилищем.
- `/health` возвращает `{"status":"ok"}` и не выполняет отдельную проверку доступности БД или дисков.
- Middleware записи сравнивает host из `Origin`/`Referer` с `Host`, когда заголовок есть. Это описание конкретной проверки, а не наличие отдельной системы CSRF-токенов.
- `backup.sh` делает SQL dump и архивирует `./runtime`, только если такой каталог есть рядом со скриптом. Compose хранит runtime в named volume `app_runtime`; этот том скрипт напрямую не архивирует. Пользовательские файлы `/mnt/storage` тоже не входят в этот backup.
- Срок хранения файлов backup по умолчанию — 14 дней; сам скрипт не настраивает расписание.
- Изменение имени Movies или storage layout требует согласования Python-конфигурации, Compose, MiniDLNA и Jellyfin.

## 12. Как продолжать разработку

- Для изменения HTTP-контракта смотреть `app/web/`, затем соответствующий сервис и SQL-модуль.
- Для изменения проводника начинать с [app/templates/app.html](app/templates/app.html): значительная часть поведения и оформления находится прямо в шаблоне. Общие тема и стили — в `app/static/`.
- При изменении схемы обновлять `init_schema()` и добавлять миграцию с отдельным именем; `tables/*.sql` не отражают всю текущую схему.
- Изменения прав доступа проверять для владельца, персонального получателя, постороннего авторизованного пользователя и анонимного посетителя; учитывать родительские папки и Movies.
- Для загрузок учитывать повторные части, отмену, восстановление после потери состояния в памяти, размер, квоту и физические пути.
- При изменении статических ресурсов учитывать недельный HTTP-кеш и версию кеша service worker.
- `README.md`, `CHANGELOG.md` и `Dokumentacija/` дают исторический контекст; поведение уточнять по актуальному коду. `serverOut.md` полезен как журнал конкретного запуска, но не описывает гарантированное текущее состояние сервера.
- Не включать локальные данные, `.env`, сессии, ключи и серверные логи в коммиты с документацией.

Этот файл следует обновлять при изменениях архитектуры, схемы, конфигурации, запуска или правил доступа.
